# Phase status

Last updated: 2026-08-04

This file records verified implementation status and external blockers. A phase is not complete merely because an interface or document exists.

## Implemented and tested

- Phase 0: streaming Claude-compatible HTTP forwarding, HTTP fidelity, fail-closed upstream errors, cancellation, and graceful shutdown.
- Phase 1: explicit standalone mode, separate local Agent Gateway lifecycle, health reporting, persistent connector-assisted Claude configuration, policy smoke tests, and standalone operations guidance.
- Phase 2, partial: browser Authorization Code with PKCE, DPoP-bound access tokens, signed-token validation, protected credential storage, refresh rotation, restart restoration, credential-generation pool isolation, local logout, and per-request managed DPoP headers. An executable mock enrollment authority derives user and key identity from validated credentials, rejects wrong keys and replayed proofs, requires explicit approval, assigns device IDs, and reports independent revocation. The connector can discover the authority and request/read enrollment with refresh-safe DPoP, reject mismatched issuer or thumbprint records, persist validated state in the protected backend, reject stale-key records, and remove local state on logout. Agent Gateway enforcement is not implemented.
- Phase 3, partial Linux data path: application routing recognizes mutually exclusive native, connector, and captured choices; captured Claude rejects inherited or persistent `ANTHROPIC_BASE_URL` routing and still fails before application launch because the prototype is not a trusted supported runtime. `agentdesktop launch` preserves arbitrary command argv and exit status, starts a gated child in a uniquely owned transient systemd user scope, resolves and validates its exact cgroup v2 path, and invokes capture preparation at that pre-release boundary. Preparation failure terminates and reaps the scope without executing the application. This is not yet capture or sandbox isolation. A pooled HTTP/2 CONNECT transport validates explicit destination ports, preserves bidirectional bytes, and reconnects lazily for later flows after observed transport loss without replaying failed flows. The Linux relay recovers `SO_ORIGINAL_DST`, bounds concurrent tunnels, and fails closed. Relay startup returns an explicit ready handle only after endpoint validation, token loading, HBONE handshake, and listener bind. For a connector-owned local Agent Gateway, Agent Desktop generates one 256-bit token in memory per Gateway process generation, injects it through the protected startup environment, and retains the same sensitive value for the in-process relay without a file round trip. The `0600` token-file path remains only for the diagnostic capture command and interoperability tests. Atomic cgroup v2/nftables setup redirects TCP/443 and rejects UDP/443. Private-container coverage validates the complete redirected kernel-to-HBONE path without sharing host network or cgroup namespaces. An opt-in real Agent Gateway smoke test validates wrong-token denial, valid-token forwarding, and HTTP/2 CONNECT interoperability. Capture activation at the launch gate, trust, relay supervision, managed HBONE authentication, real-gateway restart coverage, and production host validation remain blocked as documented below.
- Phase 4, partial: a single 36 MB self-contained development Linux standalone installer embeds a tested connector/Agent Gateway set and starter configuration, verifies independently compressed payloads, presents a guided per-user install summary, preserves user-owned Agent Gateway configuration, atomically installs/upgrades the bundle, owns verify/uninstall controls, and enables the hardened user-systemd service. The complete standalone path is validated in a clean Fedora desktop VM through the laptop mock LLM. A generic managed template and strict non-secret organization bootstrap can also produce a one-file organization-specific executable; managed MDM installation leaves identity, service activation, readiness, and separate Claude consent to the user-owned setup command. A privacy-safe local status API is implemented. Public packaging is blocked on an address-capable Agent Gateway listener or equivalent local-only transport, end-to-end managed Agent Gateway identity enforcement, and publisher signing; application-profile UI, trust workflow, binary download/update, and graphical UI also remain pending.
- Phase 5, partial: runtime platform capability reporting and a published compatibility matrix. A pinned Packer/Fedora Workstation image and QEMU lifecycle provide interactive desktop and headless CI modes, disposable qcow2 overlays, SSH control, artifact transfer, and stable guest access to explicitly forwarded laptop-loopback services. Linux native forwarding is validated; transparent capture, trust integration, installers, and macOS/Windows builds remain unavailable.
- Phase 6, partial: explicit connection, upload/response-header, and shutdown timeouts; bounded full-stream concurrency; no request retries; deterministic slow-client, timeout, overload, disconnect, malformed-request isolation, forced-shutdown, and repeated lifecycle tests.
- Phase 7, partial: JSON structured lifecycle and failure logs with fixed privacy-safe event categories; validated W3C trace-context propagation and generation; privacy-safe forwarding spans with opt-in bounded OTLP/gRPC export and orderly flush; bounded low-cardinality operational counters. Metric export and automated collector-correlation coverage remain pending.
- Phase 8, partial: hardened non-root container build and SHA-256 bundle integrity manifests with verification and tamper-safe upgrade/uninstall. Publisher signatures, staged fleet rollout, minimum-version policy, and privileged IPC remain pending.

The complete managed organization-specific walkthrough has been manually validated in the disposable Fedora desktop VM. Its MDM-owned installation half installs and verifies the bundle without adding local Agent Gateway, modifying Claude settings, or changing the existing user-service activation state. The user-owned half completes browser login, automatic test enrollment approval, service activation, separate Claude settings consent, managed gateway forwarding, and a successful request from plain `claude`. This validates the development fixtures and product journey, not production enrollment or Agent Gateway identity enforcement.

## Active blockers

- Verified device enrollment requires a production enrollment authority, authenticated administrator approval/revocation, and an agreed Agent Gateway device-identity contract. The repository's mock authority, client, and protected local records make the proposed protocol executable but are not a production trust source. A connector-generated DPoP key remains connector-instance proof and is not labeled as organizational device identity until approval is enforced end to end.
- Trusted managed identity requires Agent Gateway support for DPoP proof validation, replay protection, `cnf.jkt` binding, connector credential stripping, and immutable trusted policy context.
- Transparent capture still requires integrated relay/session supervision, managed TLS and DPoP authentication, real-gateway restart coverage, and production OS validation. The local capability token is now tied to the connector-owned Agent Gateway process generation and rotates on its next spawn; application sessions reuse it without persisting or receiving the secret. Local token enforcement, generation-safe reconnect for later flows, and real Agent Gateway HTTP/2 CONNECT interoperability are proven separately. The selected Linux mechanism is cgroup v2 with nftables, targeting an externally managed systemd scope, TCP/443 redirection, original-destination forwarding, and UDP/443 denial. Private rootless-Podman coverage validates the isolated kernel-to-HBONE path but cannot establish production host process attribution or anti-bypass guarantees. eBPF is documented as a future strengthening path.
- Standalone MITM initialization requires Agent Gateway to own CA generation and private-key loading. The current Agent Gateway source can consume file-backed dynamic-CA certificate and key material, but exposes no standalone initialization command that creates the CA and exports only its public certificate. Do not generate or read the issuing private key in Agent Desktop as a workaround.
- macOS capture, trust installation, packaging, and signing require macOS with Network Extension entitlements. Windows capture, trust installation, packaging, and signing require Windows with WFP development and signing facilities.
- Additional platform installers and the capture/trust UI depend on final package names and the first supported capture/trust platform.

## Standalone installer UX follow-ups

The target standalone user runs AI agents but is not expected to understand networking, services, health checks, configuration paths, or Agent Gateway internals. The installation journey must describe outcomes and actions in ordinary language; technical detail belongs in support reports and operator documentation.

Decisions validated in the initial Fedora walkthrough:

- Starting the product immediately and at login is the correct default.
- Readiness verification belongs to the installer. Success says the product is ready; failure gives the user an issue URL and an owner-only support report to attach.
- Connecting an installed AI agent requires consent separate from installation. Interactive setup asks after readiness; unattended `--yes` leaves agent settings unchanged unless the script also passes `--connect-agents`.
- Users invoke the manifest-owned `agentdesktop` command through the conventional `~/.local/bin` directory. The installer does not expose private helpers or edit shell startup files, refuses command-path conflicts, and verifies the link before service operations, upgrades, or removal.
- The current component, destination, and configuration details are understandable, but users may not care about them and may find them distracting. Keep them during development, then simplify the initial screen after the complete first-agent journey establishes which choices a user actually needs to make.
- The current network warning is too technical for the target user. Do not try to teach listener exposure in installer copy. Remove the need for the warning by making Agent Gateway use an address-capable loopback listener or equivalent local-only transport, then replace it with no warning unless the user must make a concrete security choice.

Revisit the initial screen before public packaging. It should answer only what will happen, whether the product starts at login, and any real choice the user must make. Installation paths, component boundaries, and network implementation details should not be prerequisites for consent.

## Next implementation steps

The next milestone is one supported Linux capture and trust lifecycle. It combines the capture-session controller with Agent Gateway MITM root distribution because redirected TLS is unusable when the selected application does not trust the issuing CA. Keep both `platform.transparent_capture` and `platform.trust_installation` false, and keep the `captured` application path unavailable, until the complete lifecycle passes the tests below.

### Certificate ownership and distribution

Agent Gateway owns TLS interception and every issuing CA private key. Agent Desktop may validate, package, install, fingerprint, and remove public CA certificates, but the connector process must never read, persist, receive through an environment variable, or log an issuing private key.

Managed remote mode uses organization-provided public roots:

1. Extend the managed customizer with a repeatable `--inspection-ca <PEM-file>` input for one or more Agent Gateway MITM root certificates. Validate that each input contains certificates only, is an X.509 CA suitable for certificate signing, is within its validity interval, and contains no private-key block or unrelated PEM object.
2. Canonicalize the certificates, record their SHA-256 fingerprints, and embed the public material in the organization-specific installer's versioned, integrity-protected customization data. Never put a filesystem path, private key, provider credential, or Agent Gateway policy in the organization bootstrap. Support an active and next root together so an organization can perform overlap rotation without replacing trust in one unsafe step.
3. Require the final customized executable to receive the organization's platform code signature after customization. SHA-256 trailer integrity is not publisher authentication, so production managed trust installation remains blocked until signature verification and the MDM deployment contract are implemented.
4. Treat system trust installation as MDM-owned. A privileged managed installation installs only the embedded public roots and records the organization ID, certificate fingerprints, trust-store locations, and installation result. The later per-user `agentdesktop connect-agents` flow must not request elevation or silently change system trust. Development deployment may extract the roots and use an explicit MDM recipe until a signed privileged installation path exists.
5. Rotation installs and verifies the next root before removing the old root. Removal must match both the ownership record and certificate fingerprint and must never remove an administrator-installed certificate merely because its subject name matches.

Standalone mode generates a distinct local CA automatically, but generation and private-key loading remain Agent Gateway responsibilities:

1. Add or use an Agent Gateway initialization command that exclusively creates a CA certificate and key in an owner-only Agent Gateway state directory and exports the public certificate. The Agent Desktop installer invokes that command without reading key bytes and configures Agent Gateway dynamic-CA TLS with the resulting paths.
2. Agent Gateway currently accepts file-backed dynamic-CA certificate and key paths and has no Secret Service, Keychain, PKCS#11, or equivalent signing-key interface. For the first increment, use a `0700` state directory, a `0600` private key, atomic exclusive creation, and no key in command-line arguments, environment variables, logs, support reports, manifests, or backups created by Agent Desktop. Do not put the key in Agent Desktop's identity credential store. Moving it into a platform keyring requires an Agent Gateway-owned secret/signing-provider interface and is a later hardening step.
3. Before changing trust, show the CA identity and fingerprint, explain that Agent Gateway will be able to inspect the selected applications' HTTPS traffic, name those applications, and require separate explicit consent plus the normal platform authorization prompt. Installation or agent-configuration consent does not imply inspection consent.
4. Install the public root idempotently in the Linux system trust store and configure an application-specific trust source when the selected application does not use that store. The Claude adapter must use its supported CA setting rather than disabling verification. Record the exact fingerprint and destinations owned by Agent Desktop.
5. On uninstall or explicit trust removal, stop every dependent captured application first, remove only matching recorded trust entries, refresh the trust store, and verify the root is no longer accepted. Delete an installer-generated CA key and certificate only after Agent Gateway is stopped and ownership is proven; never delete user-supplied Agent Gateway CA material.

### Capture-session transaction

Implement the Linux capture-session controller inside the main connector, using the existing in-process relay and narrow privileged setup helper. Do not add another product binary, change the nftables selection mechanism, or add another capture abstraction first. The controller owns one session as a transaction and performs these steps in order:

1. Validate that Agent Gateway is ready, the capture listener and HBONE addresses are loopback, the target application profile is `captured`, the required CA fingerprint is installed for that application, and neither the connector nor Agent Gateway can enter the selected cgroup.
2. Generate one unpredictable in-memory capture token before starting the connector-owned local Agent Gateway, inject it through the protected startup environment, retain it for in-process relays, and rotate it with the Gateway process. Never place it in command-line arguments, logs, or application-session IPC.
3. Start the connector's in-process unprivileged capture relay outside the application cgroup and wait for its explicit readiness before changing network rules.
4. Use the existing `agentdesktop launch` gated child and validated cgroup v2 path to keep the application stopped until trust and capture are active so no selected connection can escape during setup. The remaining work is to activate the capture transaction at that pre-release boundary and retain fail-closed cleanup ownership for the full session.
5. Invoke the narrow privileged setup boundary to preflight and atomically install the connector-owned nftables table for that exact cgroup. Only then release or launch the application in the scope.
6. Supervise Agent Gateway, relay, scope, nftables state, and the installed CA fingerprint. A relay, gateway, or trust-integrity failure keeps TCP and UDP/443 blocked for the selected scope; it never removes rules while the application can still run or retries an ambiguous flow.
7. On normal exit, cancellation, startup failure, or partial failure, stop the application scope first, remove the connector-owned nftables table second, stop the relay third, and delete the token last. Trust persists across ordinary sessions and changes only through the explicit trust lifecycle. Cleanup must be idempotent and must refuse to remove state it does not own.

### Validation and release order

Add deterministic certificate tests for malformed PEM, private-key rejection, non-CA certificates, expired or not-yet-valid certificates, duplicate roots, active/next rotation, fingerprint mismatch, idempotent installation, partial installation, application-specific trust, scoped removal, and refusal to delete unowned material. Add deterministic process-level tests for token creation, gateway readiness, relay readiness, scope creation, rule installation, application launch, gateway restart, relay exit, trust removal while in use, cancellation, and repeated cleanup.

Run the complete standalone lifecycle in the disposable Fedora VM with a real Agent Gateway performing dynamic-CA interception. Prove successful certificate validation for an intercepted HTTPS destination, TCP fail-closed behavior, UDP/443 denial, child-process capture, gateway restart recovery for later flows only, rejection after trust removal, and no residual scope, rules, relay, token, or unowned trust changes. Also test install, upgrade, CA overlap rotation, rollback, and uninstall from clean VM snapshots.

After the standalone lifecycle is proven, validate managed public-root embedding and MDM-owned trust installation in the disposable VM. Then add managed HBONE TLS and per-CONNECT DPoP validation, replay protection, `cnf.jkt` binding, credential stripping, and immutable outer-to-inner identity propagation in Agent Gateway. Re-run the managed capture journey with inner application headers attempting, and failing, to override the verified tunnel identity. Mark capture supported only after signed root delivery, trust installation, authenticated HBONE, and fail-closed process lifecycle work together end to end.

Keep `agentdesktop launch` as the stable user-facing boundary if stronger execution isolation is later justified. A Linux Bubblewrap-style namespace sandbox, a container, or a VM may implement a future explicit profile guarantee, but none is part of the current milestone. Do not call the current systemd scope a sandbox, prebuild a generic backend hierarchy, or silently downgrade when a requested backend is unavailable.
